# 转向 0.8B / 4B / OPD 的路线评估（客观意见）

日期：2026-09-26。评估对象：用户提出的六点方案（回 0.8B 部署 → 4B 重训 → OPD 蒸馏回 0.8B）。
依据：本仓库 run_config / 阶段报告 / 归档数据 + OvisOCR2 论文（arXiv:2607.13639）正文。
**本文件只做分析，不改代码、不开训。**

---

## 0. 一句话结论

方向本身**不是拍脑袋**——「SFT → 4B 分支 RL → OPD 回 0.8B → fusion」正是 OvisOCR2 论文的原始配方，
所以想走这条路是**回到论文主线**，逻辑成立。

但**当前方案的顺序是错的**：在「评测口径」和「参考译文」两个问题修好之前，
4B 与 OPD 的收益**无法被证明**（现有 chrF 被参考风格污染，见 §2.A）；
而且论文 OPD 的关键部分（teacher logits 的 top-k reverse KL）在 8GB + WSL 上**跑不了**。
建议先花 ~12h GPU 把「干净的 0.8B 基线 + 修过的评测」立起来，再决定是否上 4B。

## 1. 事实核对（逐条回应你的 1–6）

### 1.1 2B 的后训练史 —— 是「两轮 SFT + 一次失败的 GRPO(Q1)」，但要澄清两点

| run | 起止 | 底模 | seq | 结果 |
|---|---|---|---|---|
| SFT_Q1 `q1_2b` | 09-23 → 09-24, 8.4h | Qwen3.5-2B | 8192 | block_hit 0.9396，`--finetune-vision` |
| GRPO_Q1 v2 `grpo_q1_v2` | 09-24, 110 条 | q1_2b adapter | 4096 | **失败丢弃**（hit −2.4pp / sg −5.8pp） |
| SFT_Q2 `q2_2b` | 09-25, 10.7h | **q1_2b_merged** | 8192 | source 0.914，empty 0.996，chrF 0.392 |

**澄清 1：论文的 RL 不是加在部署分支上的。** 论文里 RL（GRPO）只加在 **4B teacher 分支**，
0.8B/2B 部署分支走的是 **SFT → OPD → fusion**。所以「2B 中间本该有一次 GRPO」这个说法，
严格讲**不算偏离论文**——我们真正缺的不是 2B 的 GRPO，而是**论文的 4B 分支**。

**澄清 2：那次 GRPO 失败的三条原因里，只有一条是「模型已饱和」。**
`docs/GRPO_Q1_V2.md` §6 明确写了三因：
1. 信号不足（探针 503 → 127 signal，最终 110 条，40% 组无梯度）——**能力饱和**；
2. **被迫降分辨率**（1440²/4096 vs SFT 的 2880²/8192）→ 分布外优化，越训越偏——**资源问题**；
3. 小数据 + 低 lr 仍破坏 semantic_group（−5.8pp）——**资源 + 数据规模问题**。

也就是说：**「GRPO 在这套任务上无效」这个结论的适用范围要收窄**。它证明的是
「**8GB 卡上、110 条、降分辨率**的 GRPO 无效」，不是「GRPO 无效」，更不是「Q2/多任务上无效」。
Q2 侧至今**一次 GRPO 都没做过**。

### 1.2 两轮 SFT 的真实贡献 —— 数据 > 容量

从 0.8B Q2 v1 → 2B Q2 v2 的分解（两轮之间同时改了**数据**和**基座**）：

| 变化 | 归因 | 证据 |
|---|---|---|
| empty 65.8% → 99.6%、halluc 34.2% → 0.37% | **数据修复**（清 prose 表格 / clear-on-ink / chrome 错标 + blank×1.35） | 幅度 30+pp，不可能来自换基座 |
| source 89.3% → 91.4% | 容量 + 分辨率（4096→8192） | +2.1pp |
| chrF 0.341 → 0.392 | 容量 + 数据 | +0.051 |
| Q1 block_hit 87.6% → 93.96%（sg 76.6→97.1） | **容量**（+ 分辨率） | Q1 数据同源，主变量是基座 |

**结论：这一轮真正的功臣是数据清洗；容量带来的是定位上的 +6pp、翻译上的 +0.05 chrF。**
这也顺带回答了你的第 4 点（见 §3.4）。

### 1.3 0.8B 的历史数字**不能**用来判断 0.8B 能力（至少 5 个混淆）

| 混淆 | 0.8B 旧 run | 2B 新 run |
|---|---|---|
| `max_seq_length` | **4096**（截断最密 ~10% 页） | 8192 |
| 准星面积 | 0.25%–0.425%（`_archive_v1` 实测 mean **0.00335**） | 0.08%–0.2%（mean 0.0014） |
| 负例数据 | 未清洗（625 负例，prose 表格） | 清洗后 545 |
| Q2 底模 | **`q1_grpo_merged`（已证伪的 GRPO）** | `q1_2b_merged`（纯 SFT） |
| `--finetune-vision` | **no-op bug，vision 实际被训** | 已修，Q2 真正冻结 |

→ 所以「0.8B Q1 87.6% / Q2 source 89.3% / chrF 0.341」是**一个被打过折的基线**，
不能拿来当作「0.8B 天花板」。**要回 0.8B，第一件事应该是用当前配方把 0.8B 基线重打一遍。**

### 1.4 等级：4B 本地成本粗估（RTX 4060 8GB / WSL）

| 量 | 2B 实测 | 4B 估算 | 风险 |
|---|---|---|---|
| 4bit 权重 | ~1.1GB | ~2.3GB | — |
| 训练峰值显存（8192, b2） | 3893 MiB | **6419 MiB（已实测）** | 余量 ~1.7GB；再紧就掉驱动 |
| bf16 | 5205 MiB | ~10GB | **必爆** |
| 吞吐 | 0.78 s/sample | **1.74 s/sample（已实测）** | 慢 ~2.3× |
| Q1+Q2 训练时长 | 8.4 + 10.7 = **19.1h** | **~43h**（1.5ep/1.0ep）；**~9h**（0.2–0.3 ep） | 长跑跨 WSL 重启 |
| 宿主 RAM 峰值 | ~7.3GB | **~7.0GB（已实测）** | 安全 |
| 是否能做 4B GRPO | — | **不能**（8MP×G≥4 已证伪） | — |
| 是否能做论文 OPD | — | **不能**（见 §1.5） | — |

> **2026-09-26 实测更新**：4B 本地 SFT **确实能跑**（6 步 smoke：GPU 峰值 6419 MiB / 8188，
> 宿主 RAM ~7.0GB，1.74 s/sample；Unsloth 靠梯度 offload 才装下）。
> 结论从「8GB 是硬墙」修正为「能跑但很紧：~43h 全程，或按论文 0.2–0.3 epoch 压到 ~9h」。
> 完整数据见 `eval/results/qwen4b_feasibility/`。GRPO/OPD 仍需上云。

好消息：论文的 4B 分支只训了 **0.2 epoch**（0.8B 是 2 epoch），说明大分支**不需要多训**——
若真上 4B，可以把 epoch 压到 0.2–0.5，时长可能降到 ~10h。坏消息：仍需先解决显存墙。

### 1.5 论文 OPD 的确切机制（决定本地可行性）

论文 §3.4：

- teacher = **4B + RL**（不是 4B SFT）；
- student（0.8B）**自己 rollout** 完整输出；
- teacher 在**学生的 on-policy 轨迹**上，对**学生分布 top-k 支撑集**给 log-probs；
- loss = **学生 top-k reverse KL**（mode-seeking），逐 token、按学生 top-k gather logits + chunked projection。

三个硬约束：
1. **需要 teacher 的 token 级 logits**（不是只要文本）→ 必须做 teacher 前向 + student 前向；
2. **Unsloth / TRL 没有这条路径** → 要自研 trainer（不是调参能解决的工程量）；
3. 论文之所以做 OPD，是因为**直接给 0.8B 上 RL 不稳定**（Fig.4：KL 漂移 + 表格 TEDS 掉），
   而 4B 能更稳地吸收 reward。

→ 本地 8GB **同时**驻留 4B teacher 前向 + 0.8B student 反向（还带 8k image token 激活）**不可行**；
需要 ≥24GB 卡（与 4B GRPO 同一个门槛）。

### 1.6 一个被方案忽略的关键点

**我们的 4B 不会有 RL 对齐。** 论文 OPD 的老师是「4B + 多组件 reward 的 GRPO」，
而本地跑不了 4B GRPO（§1.4）。所以「4B SFT → OPD → 0.8B」拿到的老师，
**丢掉了 OPD 收益的主要来源（reward 对齐）**，只剩「4B 的措辞 + 容量」。
这会让「通过 OPD 突破 SFT 边界」的预期大打折扣。

## 2. 三个必须先解决的「前置问题」（否则 4B/OPD 的收益无法证明）

### A. 评测口径被污染（最严重）

证据：同一模型、同一套代码，**real_labeled chrF 0.605，而合成桶只有 0.31–0.39**。
原因是参考译文来源不同：

| 桶 | 参考译文来源 |
|---|---|
| `real_labeled` | **API（deepseek-flash）**，`build_real_mt_pool.py` |
| `core_inner / multi_frag / semantic_group` | **OPUS-100**（MultiUN / TED / OpenSubtitles / KDE / GNOME…），8+ 子库混合域 |

→ 现在 chrF 同时被「模型能力」和「参考风格」污染，**不能作为 scaling 的判据**。
`both_hit_rate ≥ 0.20` 这个唯一未过门禁，很可能主要是这个口径问题的产物。
**在多参考 / COMET / LLM-judge 落地前，4B 的「突破」只是在一个坏尺子上多走一格。**

### B. 数据：真实分布只占 2.8%，参考风格混杂

Q2 train 配比实测：`core_inner 54.4% / empty_clear 15.5% / multi_frag 13.6% /
empty_special 6.9% / semantic_group 6.8% / **real_labeled 2.8%**`。
部署目标是真实截图，但训练 97% 是合成页；参考译文又来自 8+ 个不同 register 的语料 + 繁体 1.9%。
这不是「加参数」能解的，是**数据问题**——而 1.2 已经证明：数据杠杆 > 容量杠杆。

### C. 部署目标没有被量化

「2B 有点重」目前**没有数字支撑**：
- 参数量：0.8B Q4 ≈ 0.5GB，2B Q4 ≈ 1.3GB，4B Q4 ≈ 2.5GB；
- 8GB 桌面 GPU 上，0.8B 与 2B **都轻**；只有「移动/CPU/浏览器/嵌入式」才是 0.8B 的决胜场景；
- **大截图场景的瓶颈是 vision token 预填充**（2880² 页 → 数千 image token），
  0.8B 的 vision tower 是 12×768，2B 是 24×1024——**LLM 参数省下来的那点，未必能盖过 vision 的差异**。
- 仓库目前**只有训练吞吐基准**（`eval/results/qwen2b_feasibility/`），**没有端到端推理延迟基准**。

→ 先量一把「0.8B vs 2B 在真实 2–9MP 截图上的 p50/p95 延迟 + 峰值内存」，
再决定要不要为此牺牲 6pp 的定位能力。

## 3. 逐条意见

### 3.1 对第 1、2 点（确认历史 + 复盘数据）

- 历史确认无误（两轮 SFT + 一次被丢弃的 GRPO）。
- 数据**有必要调整，但优先级不是「加数据量」，而是「统一参考 + 提高真图占比」**（§2.A/§2.B）。
- 另有两处**标注歧义**值得审：`multi_frag` / `semantic_group` 的「最小语义块」边界
  （0.8B→2B 时 semantic_group 从 76.6% 跳到 97.1%，说明这类样本对模型很敏感，边界定义可能不够硬）。

### 3.2 对第 3 点（回 0.8B 部署）

**方向可以，但先别下结论。** 理由见 §1.3：0.8B 的旧数字不可信，
而「2B 太重」没量化（§2.C）。
建议：**先花一次便宜的重训（≈12–13h：Q1 ~5h + Q2 ~7.5h）拿到干净的 0.8B 基线**，
同时补一个推理延迟基准。如果干净 0.8B 的 block_hit 能到 ~90%，那回 0.8B 就很划算；
如果仍卡在 <88%（门禁），那就说明 0.8B 需要蒸馏/两阶段来补，而不是直接部署。

> 补一句：0.8B 相比 2B 的收益可能没有想象中大——旧 run 里 0.8B 与 2B 的
> **每样本训练耗时只差 ~1.5×**（0.52 vs 0.79 s/sample），因为瓶颈在 vision + 长序列。

### 3.3 对第 5 点（4B）

- 方向有论文背书（4B branch），但**本地 8GB 是硬墙**（§1.4）：训练峰值 ~6.5–7.5GB、
  bf16 必爆、**4B GRPO 和 4B-teacher OPD 都跑不了**。
- 预期收益也**不足以支撑「再次突破」**：定位已 94–96%（天花板效应），
  翻译受参考质量限制——**4B 大概率只带来 +1–3pp 定位 与 +0.02–0.05 chrF**，
  而这些幅度**小于当前评测口径的噪声**。
- 如果无论如何要做 4B，**最低风险的做法**是：
  1. 只做 4B **SFT**（4bit QLoRA，batch 1，8192 seq，**0.2–0.5 epoch**），**不做** 4B GRPO；
  2. 用 4B 做**离线序列级蒸馏**（生成/改写 → 筛选 → 训 0.8B），**不做** token 级 KL OPD；
  3. 或者直接上云（论文门槛 24GB）。
- **一个更便宜的替代 teacher**：`.env` 里的 API（deepseek-flash）在**翻译轴**上明显强于 4B Qwen，
  且零 GPU 成本。为翻译去训 4B 再蒸馏，性价比很低。

### 3.4 对第 4 点（2B 的价值）

你的表述**基本正确但可以更精确**：
- 2B 的价值不只是「证明了配方可扩展」，更具体地证明了
  **(a) 数据修复是决定性的**（empty/halluc 30+pp），**(b) 容量主要帮「组合语义」**
  （semantic_group 76.6→97.1），而**翻译只小幅受益**（chrF +0.05）。
- 反过来说：**「换更大基座 → 再突破」这个推论在翻译轴上是弱的**，
  因为翻译的瓶颈在参考数据与评测，不在参数。

### 3.5 对第 6 点（OPD 蒸馏 4B → 0.8B）

- **技术原理成立**，但有两个致命前提在本项目不满足：
  1. teacher 要**明显强于** student **且 reward 对齐**——我们的 4B 没有 RL 对齐（§1.6）；
  2. 需要 **token 级 logits + 自研 trainer + ≥24GB**（§1.5）。
- **on-policy 的另一个隐患**：论文 §3.3.1 的「on-policy filtering」和我们 GRPO 探针是同一回事——
  只保留「有时能产出更好轨迹」的样本。我们实测**只有 25% 样本有信号**。
  OPD 虽然比 RL 稳，但仍然吃同样的信号量：**student 已经 ~90% 对了，能学的空间本来就小。**
- **可落地的弱化版**（本地能做）：teacher 生成/改写 → 学生 SFT（序列级蒸馏）。
  但这就是「用强模型造数据重训」，本质是 P1(b)，**不是真正的 OPD**，收益上限低一档。
- 若真要 OPD，teacher 应该选**最强可用模型**：翻译用 API，定位用 4B（如果有 24GB 卡）。
  「4B SFT → OPD → 0.8B」这条路，**不建议在 8GB 本地做**。

## 4. 推荐的执行序列（带门禁）

| Phase | 内容 | 成本 | 门禁/决策 |
|---|---|---|---|
| **P-0 测量** | ① 统一翻译参考（同一 MT 引擎）+ 多参考/COMET 或 LLM-judge；② 真实截图端到端延迟基准（0.8B vs 2B） | 0 GPU（+API） | 能给出「与参考风格无关」的翻译分 |
| **P-1 干净 0.8B 基线** | 用**当前配方**重训 0.8B：Q1（8192/x45r/vision）→ merge → Q2（清洗数据/冻 vision） | **~12–13h GPU** | block_hit ≥0.90 且 empty ≥0.98 → 回 0.8B 可行；否则先补数据 |
| **P-2 翻译增强** | 零 GPU 试点：现有 `pred_source` + API MT，测 oracle/pred 两档 chrF & both_hit | ~15 min 网络 | 若 oracle chrF ≥0.55 → 两阶段落地 |
| **P-3 4B（条件性）** | 仅当「P-1 不达标 + P-0/P-2 已修好 + 有 ≥24GB 卡」时做；先只做 4B SFT 0.2–0.5 epoch | ~10–40h | 4B 相对干净 2B 的提升 >2pp 才值得 |
| **P-4 OPD** | 需 24GB+ 卡 + 自研 top-k reverse-KL trainer；否则退化为序列级蒸馏 | 高 | teacher 必须 ≥4B 且有 RL/强 MT 对齐 |

## 5. 需要你拍板的三个问题

1. **部署目标到底是什么？**（桌面 GPU / 移动 / CPU / 浏览器；内存与延迟预算）
   —— 这决定 0.8B 是不是**必须**，以及 2B 是不是其实完全够用。
2. **有没有 ≥24GB 卡或云预算？**
   —— 这决定 4B GRPO 与真 OPD 是否**可能**（论文的门槛）。
3. **更看重「定位」还是「翻译」？**
   —— 定位：0.8B/2B 已接近天花板，收益靠数据；翻译：参考与评测未修，应先修口径。

> 我的建议（一句话）：**先做 P-0 + P-1（~12h GPU 的 0.8B 干净基线 + 修评测），拿到可信的对照后，
> 再决定值不值得为 4B/OPD 付 30–40h 和一张更大的卡。** 现在的方案不缺雄心，缺的是「能证明收益的尺子」。
