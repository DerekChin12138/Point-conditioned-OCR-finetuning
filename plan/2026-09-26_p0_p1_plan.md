## 1. P0 — Studio 目视验收方案

目标：用 `checkpoints/q2_2b_merged` 回答四问 —— ①XML 是否成对 ②空例是否仍空 ③Q1 跟点是否回退 ④译文是否可读。
重点抽样 `semantic_group` / `multi_frag`。**只做推理，不训任何东西。**

### 1.1 已完成的准备（零 GPU）

1. 离线 join + 逐条打分（`p0_cases` 全 2684 条，含 point/bbox/area/GT/pred/各项指标）。
2. 生成 **75 条分层抽验清单**（`p0_selection`），构成：
   - 全部异常行（截断 9 / 未闭合 3 / `<body>` 泄漏 1 / 幻觉 2，去重后 ~14 条）；
   - 每个正例桶 `core_inner / multi_frag / semantic_group / real_labeled` 的 **worst 6 + 中位 4 + best 3**（按 source edit）；
   - `semantic_group` 再按 **chrF 最低 6 条**（翻译轴）补抽。
3. 复核 studio 与评测走**同一个** `generate_point_text` + `resize_for_ovis` 路径，
   `/api/generate` 支持传 `area_frac`（用每条**原始** `marker_area_frac` 复现）、`prompt`、`x/y`、`image`(base64)。

## 2. P1 — 提升翻译质量：对比方案（先给对比，不先动手）

前提结论：source 侧已 91.4%（点了已不是瓶颈），`both_hit` 卡在**翻译**。四条路线的性价比：

| 路径 | 机制 | 预期收益 | 成本（本地） | 风险 | 本地可行性 |
|---|---|---|---|---|---|
| **(a) 两阶段** | Q2 权重只做点 OCR → `<source>` 交给**纯文本** MT 模型/API | `translation_chrF` 上限最高；`both_hit` 有望 0.30–0.50+（取决于 MT 强度） | **推理期多一跳**；零重训 | 线上延迟 +1 次调用；需固定 MT 版本 | ✅ **先做零 GPU 试点即可判定** |
| **(b) 蒸馏** | 用强 MT 重新生成 **train 38499 正例**译文，重训 SFT_Q2 | 与 (a) 同量级上限，但把能力烧进 2B；`both_hit` ↑ | API ~4–9h + 重训 **10.7h** + 重评 1.8h | 评测参考被换 → 指标不可与原 GT 直接比；要另立 held-out 参考 | ⚠️ 需一次完整训练 |
| **(c) 繁体清洗** | 把参考译文里 ~1.9% 繁体/噪声转简体重训 | **收益最小**（只动 2% 数据，且用户看到的模型输出本就是简体） | 需 opencc + 重训 10.7h | 低 | ⚠️ 性价比最低，除非顺手 |
| **(d) Q2 GRPO** | RL 直接优化 q2 reward | 未知，Q1 已证明本地信号不足 | 需 24GB 卡 + ≥500 signal | 高 | ❌ 本地不可行 |

### 2.1 推荐：先跑 (a) 的**零 GPU 试点**（不训任何模型）

利用已有 `final_predictions.jsonl` 的 2139 条 `pred_source`（真实 91.4% 命中）+ `.env` 的 MT API，
分层抽 400 条正例（4 桶按比例 + 补 `semantic_group`/`multi_frag`），度量：

| 变体 | 含义 |
|---|---|
| **oracle-source → MT** | 用 GT source 翻译，得到**两阶段的质量上限** |
| **pred-source → MT** | 用模型实际 source 翻译，得到**端到端可用率** |
| 现有 2B 端到端 | 基线 chrF 0.392 / both 0.173 |

指标：`translation_chrF2`、`translation_hit(≥0.6)`、`both_hit`、CJK 比、长度比、繁体残留率。
（顺带量化 (c)：用同一 MT 或 opencc 统计参考译文的繁体真实占比与其对 chrF 的拖累。）

**决策规则**：
- 若 **oracle-source chrF ≥ 0.55 且 pred-source both_hit ≥ 0.30** → (a) 明显值当 → 落地两阶段（写推理封装 + studio 开关），(b) 作为可选「烧进模型」升级。
- 若 oracle 上限也 < 0.45 → 说明是**评测口径/参考译文**问题（chrF 单参考太保守），应转用 COMET / 多参考，而不是继续重训。
- (c) 仅当繁体占比被证明显著（>3%）且拖累 chrF >2pp 时才做。

**试点成本**：400×2 次 API 调用（并发 5）≈ 10–15 min，纯 CPU/网络，零 GPU、零训练、不动权重。

### 2.2 若试点判定要「烧进模型」：P1(b) 管线（需你二次确认）

1. 用 MT 重译 train 正例（只替换 `<translation>`，`<source>` 与空例不动，保持 XML 格式）；
   估计 38499 条 × ~600 tok ≈ 23M token，并发 8 约 4–9h（夜间）。
2. 重训 SFT_Q2：与现配方**完全同参**，只换 train 译文 → `checkpoints/q2_2b_distill/`（10.7h）。
3. 评测：新增 held-out 参考（同 MT 生成，防自证）+ 保留原 OPUS 参考做旁证，对比 `both_hit`。
4. merge → 替换 `q2_2b_merged`（保留旧整模做回滚）。

> 注：蒸馏会让「与原 OPUS 参考的 chrF」不再可比。因此必须先建 **独立 held-out 参考**（模型没见过、MT 与训练同版本），否则数字会虚高。
